# Авто-агент механика — бриф проекта

Конспект рабочего чата (Алиса, 2026-11-26). Единственный пользователь инструмента — автор проекта
(начинающий механик). Не для продажи; доступ максимум коллегам того же сервиса, база наружу не выкладывается.

## 1. Контекст

- Сервис работает с китайскими марками (Changan — основной) + VAG + Lada.
- Опытные механики инструментом пользоваться не будут (работают «вижу деталь — открутил — заменил»).
  Переучивать их не нужно: агент строится под себя, как замена отсутствующего наставника.
- Опыт мастеров собирается автором лично (подошёл, спросил, записал), постфактум — механиков не нагружаем.

## 2. Автомобили

- **Старт (бесплатные русские мануалы):** VW Polo, Skoda Rapid (1.6 MPI / 1.4 TSI), Lada Kalina
  + документация StarLine (S96 v2: установка, эксплуатация, карты подключения).
- **Второй этап:** Changan (CS95, CS75 Plus, UNI-K/UNI-V/UNI-S, CS55 Plus) — китайские сервисные мануалы
  через портал ATS (ats.changan.com.cn, подписка, ~¥60/день). Качать по VIN-листу реальных заездов,
  с человеческим темпом. **Маскировку бота не делаем** — это обход защиты, отказались осознанно.

## 3. Архитектура базы знаний — 6 сущностей

1. **Текстовые чанки** мануалов: перекрытие ~200 токенов, метаданные «модель / раздел / страница»,
   векторный поиск на мультиязычной модели (bge-m3 / multilingual-e5). Китайский индексируем как есть,
   переводим только оглавления/подписи; числа и артикулы не переводить.
2. **Справочные таблицы → JSON** (моменты затяжки, заправочные объёмы, распиновки, регламенты ТО,
   предохранители/лампы): каждая таблица — атомарный объект с метаданными (модель, раздел, страница,
   название кит.+рус). Поиск: вектор по названию таблицы → точная выборка строки по ключу.
   Так невозможно «сместиться на соседнюю строку», как в векторном чанке.
3. **Электросхемы** = файлы-ассеты + текстовые метаданные (заголовок, компоненты, коды разъёмов, страница).
   Пин-ауты — в JSON. Векторизовать саму картинку схемы не нужно. Опционально: VLM-описания.
4. **Картинки мануалов**: карточка `{image_id, model, doc, page, figure, caption_cn/ru, related_chunks, type}`.
   Привязка к чанкам по номеру рисунка (图 3-15) и странице. Хранить в исходном разрешении.
5. **Карточки кейсов** (свой опыт): `{car, vin_partial, symptom, dtc, diagnosis, solution, time_spent,
   pitfalls, mechanic, date, photos, verified}`. В базу — только `verified: true`; подавать как опыт, не истину.
6. **Каталог оборудования сервиса**: `{tool_id, name, category, location, photo[], manual_pdf, quick_guide,
   notes, calibration{last, interval}}` — с реальными фото и локальным знанием («левая головка тугая»).

### Слой маршрутизации (до поиска)

- Каталог моделей JSON с алиасами (русское имя / китайское / имя в ATS / заводской код).
- Метаданные каждого документа: модель, поколение, годы, рынок (CN ≠ RU), комплектация (2WD/AWD, iDD), тип.
- Векторный поиск — с фильтром по метаданным; более узкий документ выигрывает.
- Неоднозначность (UNI-K vs UNI-K iDD, 2WD vs AWD) → уточняющий вопрос, не ответ наугад.
- VIN (первые ~11 знаков) → отсекает модель/год/рынок.

## 4. Правила агента (антигаллюцинации)

- Отвечать **только** по найденным фрагментам; всегда источник: документ, раздел, страница.
- Нет данных → «в базе не найдено». Моменты затяжки сочинять запрещено — это главный риск.
- Приоритет: оборудование и практика сервиса → мануал модели → общие методы из интернета (как запасной
  вариант, явно помеченный). Пример-эталон: «развал Kalina» → стенд из каталога, а не «верёвка с грузом».
- Разделять источники в ответе: «по мануалу — так, у нас в базе — 3 кейса, в 2-х виноват был X».
- Значения (углы, моменты, допуски) — из мануала машины; процедуры измерения — из инструкции стенда.

## 5. Слои поверх RAG

- **Фото-вопросы:** механик фотографирует деталь → VLM с контекстом (машина, где снято) → гипотеза →
  текстовый RAG (процедуры/моменты) + визуальный индекс иллюстраций мануала (SigLIP / jina-clip) →
  ответ «что это + картинка из мануала с номерами деталей». Координаты/рамки надёжнее у
  Qwen2.5-VL / Gemini (grounding); у GPT/Claude координаты нестабильны. Не опозналось → «не нашёл», не угадывать.
- **Технологические процессы (чек-листы):** шаблон процедуры (замена масла и т.п.), значения шагов
  (объём, момент пробки) подтягиваются из базы под конкретную модель. Каждый шаг — отметка «выполнено»
  с временем → снимает вопрос «а закрутил ли я пробку» (шаг 6, 14:32). Завершённый воркфлоу
  **автоматически = карточка кейса**.
- **Журнал работ / наряды:** `{date, car, work, workflow_done, hours, rate, amount, paid}` →
  месяц → сумма по расценкам → сверка с расчётным листком («правильно ли выплатили»).
  Это личный учёт, не бухгалтерия: сверять мягко, не через голову в претензию.

## 6. Первый боевой кейс: Rapid + StarLine S96 v2

Симптом: штатный ключ снимает штатную охрану **без метки** → дверь открывается, StarLine орёт.
Цель: пока метки нет — штатный брелок не открывает машину вообще.

- Терминология StarLine: нужна **«Блокировка радиоканала»** (брелок мёртв без метки),
  а не «Запрет снятия с охраны» (дверь всё равно откроется + тревога — текущее поведение).
- «Авторизация владельца» в StarLine Мастер — базовая опция, включается первой.
- На Rapid **нет Kessy** в любых комплектациях → «отрезать питание антенны» нечего; приёмник встроен
  в блок электрики. Варианты: (1) CAN-команда — проверить наличие в библиотеке can.starline.ru
  под конкретный год/кузов; (2) **релейная блокировка цепей ЦЗ** нормально-замкнутыми реле с допканала —
  работает на любой машине, самый надёжный путь. Механический замок ключом это не закрывает — предел системы.
- Автозапуск (если когда-нибудь): 1.4 TSI — обход по CAN через VAG-01 (~12 000 ₽), 1.6 MPI — только обходчик со вторым ключом.

## 7. Приоритет MVP (итог чата)

1. **Журнал работ + один воркфлоу** («замена масла», Rapid) — простая веб-морда, телефон в том же Wi-Fi,
   отметка шага прямо у машины. Польза с первого дня, технически проще RAG (CRUD + состояния, без эмбеддингов).
2. **RAG-база** — начать с бесплатных русских PDF (эксплуатация Rapid с сайта, мануалы StarLine S96):
   чанки + таблицы + картинки, правила агента из §4. Встраивается внутрь воркфлоу и в чат.
3. **Фото-вопросы** — потом, когда текстовая база заработает.

## 8. Техстек (черновой)

- Окружение: **uv** + виртуальное окружение `.venv`. Зависимости — в `pyproject.toml`,
  `uv sync` / `uv run`; `uv.lock` в git, `.venv` — вне git.
- Python: httpx/requests (выгрузка), PyMuPDF (`find_tables()`, `get_images()`, рендер страниц 300–400 dpi),
  pdfplumber/Camelot для сложных таблиц; OCR — только для сканов без текстового слоя.
- Эмбеддинги: текст — bge-m3 / multilingual-e5; изображения — SigLIP / jina-clip.
- Векторная БД с фильтрацией по метаданным: Qdrant / Chroma; коды ошибок и артикулы — гибридный поиск
  (точный, не векторный).
- LLM по API (для китайского текста Qwen особенно хорош); локально — опция через Ollama.
- Критичные таблицы после извлечения — ручная сверка с оригиналом (числа 0/8, 1/7 в OCR).
- Контроль качества: эталонный набор 15–20 вопросов с известными ответами, гонять после каждого
  изменения индекса; плюс «вопрос про то, чего в базе нет» → должен ответить «не найдено».

## 9. Чего не делаем

- Не продаём, не выкладываем базу наружу, не обсуждаем перепродажу контента ATS/OEM.
- Не маскируем бота при выкачке; темп человеческий, только по VIN-листу.
- Не строим конкурентную CMS для сервиса — только личный журнал.
- Не переводим весь массив мануалов; не пишем свою LLM.
- Не пытаемся «внедрить» инструмент механикам — пользователи: автор (и пассивно — коллеги, когда спросят).

## 10. Интерфейс (схема, 2026-11-26)

Ядро — FastAPI, к нему три «двери»:

1. **Чаты — готовый UI, не самописный.** Open WebUI (docker) подключается к нашему FastAPI как
   OpenAI-совместимый провайдер: `POST /v1/chat/completions` + стриминг SSE. История диалогов,
   загрузка файлов, мобильный браузер, вход по логину — из коробки. Альтернативы: LibreChat, AnythingLLM.
   Этап 0 (вечер, без своего кода): Open WebUI со встроенным RAG («Знания») — потрогать формат;
   затем логику переносим в ядро: таблицы JSON, маршрутизация по модели, антигаллюцинационные правила.
2. **Воркфлоу + журнал — свои 2–3 страницы** на REST того же FastAPI (кнопки «выполнено», таблица
   нарядов). В чат не пихать: это формы и состояния, не диалог.
3. **MCP — позже, отдельная дверь.** FastMCP-слой с инструментами `search_manuals`, `get_torque`,
   `workflow_*`, `journal_*` — чтобы агенты в Claude Desktop / DSH / других MCP-хостах работали
   по нашей базе. MCP — не протокол чат-интерфейса: «готовые UI, дёргающие MCP» — это агентские хосты
   со своей моделью на клиенте.

Модель LLM: Qwen по API (китайский текст) или Ollama локально — выбирается внутри ядра, UI прозрачно.

Не делаем: собственный чат-фронтенд с нуля (React+сокеты); mcpo-прокси — только как последний мост.
