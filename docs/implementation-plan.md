# План реализации — этапы

Рабочий план к [project-brief.md](project-brief.md). Принцип: **каждый этап заканчивается
работающей вещью**, которую можно потрогать. Не переходим к следующему этапу, пока предыдущий
не прошёл свои критерии готовности. Код пишем только внутри текущего этапа.

Единица планирования — «вечер» (1–3 часа). Оценки для одного человека, без спешки.

```
Зависимости:
0 → 1 → 2 → 3 ─┬→ 6 (фото)
        ↘       ├→ 7 (Changan/ATS)
          4 → 5 └→ 8 (MCP, опционально)
```

Этапы 4–5 от чата не зависят — их можно поднять выше, если нужна польза «с первого дня».

---

## Этап 0. Фундамент и разведка — 1–2 вечера

**Цель:** окружение поднято, материалы собраны, решения приняты.

- Структура репозитория: `app/` (ядро), `docs/`, `data/` (PDF/индексы — в git не идут), `config/`.
- Python-окружение: **uv** + виртуальное окружение `.venv` — зависимости в `pyproject.toml`,
  `uv.lock` в git, `.venv` вне git; все команды проекта через `uv run`.
- Docker: поднять Open WebUI (docker-compose), потрогать встроенный RAG «Знания» на двух PDF.
- Собрать бесплатные документы: руководство по эксплуатации Rapid (сайт changanauto.ru / VAG),
  Polo, Kalina (Легион-Автодата-подобные PDF), мануалы StarLine S96 v2 (установка + эксплуатация).
- Завести локальные секреты (`.env` вне git): ключ провайдера LLM.
- Решить: основной провайдер (рекомендация — DeepSeek, запасной — GLM/Qwen), где эмбеддинги
  (bge-m3 локально в Ollama).

**Готово, когда:** Open WebUI открыт с телефона в Wi-Fi, вопросы по загруженному PDF отвечаются
встроенным RAG; секреты не светятся в git.

## Этап 1. LLM-ядро и чат — 2–4 вечера

**Цель:** свой бэкенд отвечает в готовом чате, провайдер — строка в конфиге.

- Транспортный слой: один OpenAI-совместимый класс провайдера (base_url + ключ + модель +
  флаги возможностей: vision / tools / json / длина контекста).
- Реестр провайдеров в конфиге (YAML/JSON): DeepSeek, Qwen, GLM, Ollama — как настройки одного класса.
- Слой агента v0: системный промпт с правилами брифа §4 (только по найденному, всегда источник),
  стрим ответа (SSE).
- Эндпоинт `POST /v1/chat/completions` (OpenAI-совместимый); провайдеры публикуются как
  модели-алиасы (`deepseek-chat`, `qwen-max`, …) — выбор поставщика прямо в списке моделей UI.
- Лог стоимости: токены/запрос в SQLite.
- Эталонный QA-набор v0 (15–20 вопросов с известными ответами) — пока на общие вопросы,
  гоняется скриптом.

**Готово, когда:** в Open WebUI видны модели-алиасы; ответ стримится; смена провайдера =
правка конфига, ноль кода; скрипт QA прогона пишет таблицу результатов.

## Этап 2. Конвейер документов — 1–2 недели вечерами

**Цель:** «единый парсер мануала» — сердце базы (бриф §3).

- PDF → текст: PyMuPDF; для сканов без слоя — OCR (отдельно, не в основном пути).
- Чанки с перекрытием ~200 токенов, метаданные «модель / раздел / страница / тип документа».
- Таблицы → JSON: PyMuPDF `find_tables()`, сложные — pdfplumber; каждая таблица = атомарный
  объект (модель, раздел, страница, название кит.+рус, тип: моменты/объёмы/распиновки).
  Критичные таблицы (моменты затяжки) сверить руками с оригиналом.
- Картинки: `get_images()` + рендер страниц 300–400 dpi; карточка `{image_id, model, page,
  figure, caption, related_chunks, type}`; привязка к чанкам по номеру рисунка; фильтр мусора
  (логотипы/иконки) по размеру и позиции.
- Каталог моделей (JSON) с алиасами + обязательные метки рынка/комплектации на каждом документе.
- Приёмка: `inbox/` → манифест (SQLite: doc_id, хеш, статус) → статусы `indexed /
  needs_review / failed`; замок от двойного запуска; запуск вручную командой; успешные
  файлы переезжают в `library/` по структуре из раздела «Структура папок и именование».

**Готово, когда:** команда «распарси PDF» выдаёт `chunks.jsonl` + `tables/*.json` + `images/`
с карточками; эталонная таблица моментов Rapid совпадает с оригиналом построчно.

## Этап 3. RAG-поиск и правила агента — около недели

**Цель:** агент отвечает по базе с цитатой и умеет говорить «не найдено».

- Эмбеддинги: bge-m3 локально (через Ollama или sentence-transformers).
- Векторная БД с фильтрацией по метаданным (Chroma для старта; Qdrant — если понадобятся
  тяжёлые фильтры). Поиск-маршрутизация: модель/поколение/рынок → фильтр до векторов,
  узкий документ выигрывает.
- JSON-таблицы: вектор по названию таблицы → точная выборка строки по ключу.
- Гибридный поиск для кодов ошибок и артикулов (точный, не векторный).
- Правила агента в системном промпте: приоритет оборудования сервиса → мануал → общие методы
  (запасной вариант, помеченный); разделение источников «по мануалу / из кейсов».
- Вопросы-уточнения при неоднозначности (2WD/AWD, поколение) — прежде чем искать.

**Готово, когда:** QA-набор отвечает с указанием документа и страницы ≥ 90%; вопрос про то,
чего в базе нет, получает «не найдено», а не фантазию; «момент затяжки пробки Rapid» = точное
число из JSON + страница.

## Этап 4. Воркфлоу + журнал — около недели (независим от этапов 2–3)

**Цель:** польза с первого дня — страховка от пропущенного шага и учёт зарплаты.

- SQLite: шаблоны воркфлоу, шаги, выполнения (шаг + отметка времени), журнал нарядов
  `{date, car, work, hours, rate, amount, paid}`.
- REST на том же FastAPI + 2–3 страницы (кнопка «выполнено» прямо у машины с телефона).
- Шаблон «замена масла» под Rapid; значения шагов (объём, момент пробки) подтягиваются из базы
  этапа 3, когда он готов; до того — руками из мануала.
- Завершённый воркфлоу автоматически = карточка кейса.
- Экран «месяц»: сумма по расценкам, сверка с расчётным листком.
- Кнопка «Проиндексировать» + страница статусов конвейера (фоновая задача, прогресс), ночной
  schedule и триггер «разобрать inbox при старте сервиса».

**Готово, когда:** первая реальная работа сделана по чек-листу с телефона; журнал показывает
сумму за месяц; «закрутил ли пробку» решается просмотром отметки шага.

## Этап 5. Кейсы и каталог оборудования — 2–4 вечера

**Цель:** база начинает накапливать то, чего нет ни в одном мануале.

- Карточки кейсов (свой опыт, постфактум): `{car, symptom, dtc, diagnosis, solution, pitfalls,
  photos, verified}`; в индекс — только `verified: true`; подача как опыт, не истина.
- Каталог оборудования: карточки с реальными фото, инструкциями, местом, полем notes,
  календарём калибровок.
- Правило приоритизации в промпте (бриф §4) + эталонный тест «развал Kalina» → стенд, не верёвка.

**Готово, когда:** 5–10 своих кейсов в базе и агент отвечает «по мануалу так, у нас в базе —
случай такой-то»; вопрос про стенд возвращает инструкцию твоего стенда со страницей.

## Этап 6. Фото-сценарий — около недели

**Цель:** «что это за деталь?» по фотографии.

- Vision-провайдер в реестре (qwen-vl / GLM-4V) + правила промпта («не опознал — так и скажи»).
- Визуальный индекс иллюстраций мануала (SigLIP / jina-clip): фото механика → похожие фигуры
  из мануала с номерами деталей.
- Ответ: текст (гипотеза + процедура + момент из JSON) + иллюстрация из мануала; рамка на фото —
  только если модель отдаёт координаты надёжно (grounding).
- Загрузка фото через Open WebUI; VIN/номерные знаки в кадр не отправлять.

**Готово, когда:** фото типовой детали даёт гипотезу + страницу мануала; фото мусорного кадра
получает честное «не смог определить».

## Этап 7. Changan / ATS — после стабильного этапа 3

**Цель:** второй контур базы — китайские сервисные документы по реальному парку сервиса.

- VIN-лист моделей, реально заезжающих в сервис (CS95, CS75 Plus, UNI-K/V/S, CS55 Plus…).
- Подписка ATS; выгрузка только по VIN-листу, человеческий темп, без маскировки бота (решено).
- Тот же конвейер этапа 2 на китайских PDF: индекс — оригинал (bge-m3 мультиязычный),
  переводы — оглавления и подписи таблиц; числа не переводить; проверка OCR/текстового слоя.
- Каталог моделей пополняется алиасами (кит. имя / имя в ATS / заводской код), правила рынка
  CN vs RU в маршрутизации.

**Готово, когда:** вопрос «момент болтов хвостовика CS95 AWD 2023» находит китайский раздел,
агент отвечает на русском с цитатой и страницей.

## Конвейер пополнения базы (ingest)

Связывает этапы 2 и 3: как база живёт после первичной сборки.

```
data/inbox/            ← сюда кидаются новые файлы (единственное ручное действие)
   │ 1. SHA-256 файла
   ▼
Манифест (SQLite, таблица документов)
   ├─ хеш существует        → пропуск, «дубликат»
   ├─ имя то же, хеш другой → переиндексация: снос старого по doc_id, парсинг заново
   └─ новый файл            → парсинг (чанки/таблицы/картинки) → метаданные
        ├─ распознаны       → эмбеддинги → индекс → статус indexed
        └─ не распознаны    → статус needs_review (карточка в UI)
```

- Успешные файлы конвейер перемещает из `inbox/` в `library/` по полной структуре (см. следующий
  раздел) — пустой inbox = всё обработано.
- Статусы: `new → processing → indexed | needs_review | failed` (с причиной: «нет текстового
  слоя, нужен OCR» и т.п.). Один сломанный PDF не останавливает партию; после прогона — отчёт.
- Смена модели эмбеддингов или параметров чанков = полный переиндекс по файлам из `library/`;
  версия модели эмбеддингов хранится у каждого чанка. Оригиналы PDF — источник истины.
- Удаление мягкое: файл убрали из `library/` → `archived`, из индекса сносится только явно.
- Кейсы мастеров — та же труба без PDF-парсинга: одна карточка = один вектор; поля JSON — истина;
  в поиск попадают только `verified: true`; правка карточки → новый хеш → переэмбеддинг.
- Запуск конвейера (триггеры, по мере появления):
  - **CLI «проиндексируй сейчас»** — с этапа 2; работает без веб-сервиса, напрямую с базой;
  - **кнопка «Проиндексировать» + страница статусов** — с этапа 4; запрос запускает фоновую
    задачу и сразу возвращает ответ, прогресс виден на странице;
  - **по расписанию** (ночь, ~03:00) — планировщик в процессе приложения (меньше движущихся
    частей); systemd timer — запасной вариант;
  - **при старте сервиса** — разобрать всё накопленное в inbox за ночь: утреннее «включил ПК
    в гараже» само становится триггером приёмки;
  - **watcher папки** (inotify/watchdog) — сознательно отложен: ручной запуск + ночь + кнопка
    покрывают ~95% сценариев, мгновенность не критична.
- Замок от двойного запуска — обязательная логика с этапа 2: флаг «конвейер занят» в базе;
  второй триггер ждёт или отвечает «уже идёт, вот статус». Хеш-дедупликация делает двойной
  запуск безвредным, но параллельные прогоны не нужны.
- Отчёт каждого прогона пишется в журнал и виден из CLI и из UI: новых / дубликатов /
  ошибок / needs_review.
- Ручной минимум пользователя: (1) файл в `inbox/` или карточку в `cases/`; (2) заполнить
  `needs_review`; (3) подтвердить черновик каталога при первой незнакомой модели.
  Всё остальное — работа системы.

## Структура папок и именование (метаданные из пути)

Принцип: путь = шаблон метаданных; **дерево строит конвейер по метаданным, а не человек руками**.
Человек только кладёт файл в `inbox/` и при необходимости заполняет карточку review.

```
data/
  inbox/                                ← ручной вход
  library/                              ← раскладывает конвейер
    <бренд>/                            ← ур.1, latin slug = ключ каталога моделей
      <модель>/                         ← ур.2, ключ каталога
        <поколение>/                    ← ур.3, «2016-2020» или «универсал»
          <тип-документа>/              ← ур.4, контролируемый словарь
            <раздел>/                   ← ур.5, контролируемый словарь (опционально)
              <название>.pdf            ← ур.6, свободное имя, дефисы вместо пробелов
  cases/                                ← опыт мастеров, уровни 1–3 те же + JSON-карточки
  equipment/                            ← оборудование сервиса: equipment/<tool_id>/...
```

Примеры:

- `library/volkswagen/polo-sedan/2016-2020/ремонт/двигатель/замена-грм.pdf`
- `library/skoda/rapid/2016-2020/схемы/электрика-полная.pdf`
- `library/changan/cs95/2020-2025/cn/ремонт/...` — рынок `cn` явной папкой (по умолчанию `ru`)
- `library/starline/s96-v2/универсал/установка/карта-подключений.pdf`
- `cases/volkswagen/polo-sedan/2016-2020/2026-11-26__грм__не-заводится-после-мойки.json`

Контролируемые словари (будущие фильтры БД и пункты навигации UI):

- тип документа: `ремонт`, `схемы`, `эксплуатация`, `то`, `каталог`, `бюллетень`, `установка`;
- раздел: `двигатель`, `трансмиссия`, `электрика`, `кузов`, `подвеска`, `тормоза`,
  `отопление-кондиционирование`, `салон`, `прочее`;
- суффиксы имени файла: `__4wd`, `__idd`, `__cn` (комплектация/рынок, если не в папке).

Источники метаданных: уровни 1–3 → brand/model/generation; ур.4 → doc_type; ур.5 → section;
имя файла → title + суффиксы; оглавление PDF → сверка разделов; карточка review → ручные правки.

Правила:

- минимум для индексации: бренд + модель + поколение + тип; иначе `needs_review`;
- незнакомый бренд/модель → черновик записи в каталоге моделей + подтверждение одной кнопкой;
  каталог моделей — единственный источник имён и алиасов для разбора запросов;
- поля JSON-карточки кейса приоритетнее папки; расхождение → предупреждение в отчёте;
- полный мануал одним PDF может лежать без ур.5 — разделы определятся из оглавления при парсинге;
  нарезанные по разделам документы (erWin/ATS) ложатся глубже;
- словари расширяются осознанно — каждое значение становится фильтром поиска.

## Сквозные практики (действуют во всех этапах)

1. **QA-эталон** — дополняется на каждом этапе; смена провайдера/индекса = обязательный прогон.
2. **Секреты** — только в локальном `.env`, в git никогда; ключи коллег (если будут) — отдельные.
3. **Данные вне git** — `data/` в `.gitignore`; бэкап папки с PDF/индексами — по расписанию.
4. **Каждая ошибка агента** → новое правило маршрутизации/промпта или карточка в QA-набор.
5. **Ответ без источника = баг**, а не ответ.
6. **Инструментарий Python: uv + `.venv`** — установка зависимостей только через `uv sync`,
   запуск только через `uv run`; `uv.lock` коммитится, `.venv` игнорируется.

## Открытые вопросы (решаются по ходу)

- Оплата API из РФ (DeepSeek/Alibaba напрямую или через посредника) — влияет на выбор основного.
- Есть ли ключи/подписки GLM/Qwen/Kimi фактически — сколько провайдеров класть в реестр на старте.
- Свободные ресурсы ПК под bge-m3 (нужно ~2–4 ГБ RAM) — если впритык, эмбеддинги на время в API.
